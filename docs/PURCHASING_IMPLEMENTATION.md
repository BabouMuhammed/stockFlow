## What changed

- Stock receipts accept up to 100 different products in one transaction. Quantity,
  purchase price, line total, overall total, supplier, reference, date, and notes are
  visible. Legacy single-product API requests remain supported.
- The backend validates products/suppliers within the current business, prices and
  quantities, calculates all amounts, and atomically records stock, items, and audit
  history. Positive quantities support three decimals; money uses integer bututs.
  Extended costs round half up once per line. Overflow and duplicate product lines
  are rejected. Zero-cost goods remain supported, without silently rounding prices.
- Idempotency protects receipt and payment retries. Supplier/reference repeats
  require an explicit reason, allowing repeat deliveries and legacy split invoices.
- Supplier settlements have a separate append-only ledger. Multiple payments,
  partial/full settlement, dated payment history, and current outstanding balances
  are supported. Overpayment, tenant mismatch, missing confirmation and invalid
  amounts are rejected. External payments require a reference and manual confirmation;
  this does not claim bank/provider verification or transfer funds.
- Reversals append offsetting entries and preserve originals. PostgreSQL prevents
  ledger mutation and validates reversal identity/amount/method and overpayment.
  API locks and serializable retries protect concurrent submissions.
- Historical purchases remain UNRECONCILED. An owner can record known payments and
  explicitly confirm complete historical reconciliation with a reason. They are not
  presented as confirmed debts before reconciliation. Legacy receipts lacking a
  supplier need a separately reviewed provenance repair; no supplier is fabricated.
- Existing Suppliers screens expose financial overview, purchase history, payment
  history, receipt details, and current verified debt separately from uncertain history.
- Reports show received inventory value by receipt date, supplier net outflow by
  payment/reversal date, current verified supplier debt, and unreconciled purchase
  value. Payments/purchases never automatically become operating expenses.
- Obvious new inventory/COGS/supplier-settlement expense categories are blocked.
  Suspect historical categories are flagged, retained, and still included in expenses
  until explicitly corrected. This is a safeguard, not semantic detection of every
  possible misclassification.
- Archived products with stock remain in valuation. Trend/product COGS and revenues
  now account for returns on their event dates, consistent with summary treatment.
  Product CSVs use the same net-return calculation. Category/cashier breakdowns stay
  explicitly labelled before returns. CSV valuation uses exact integer extension.
- Forms retain their contents on errors, show pending states, guard rapid submits,
  and use accessible labels. Tables scroll inside their containers. Nested dialogs
  have distinct accessible title IDs. Negative report bars support refund-only days.
- Readiness checks detect missing purchasing migrations. POS pricing, payment
  authorization, discounts and checkout calculations were not rewritten.

## Database migration and compatibility

The new additive migration adds nullable `StockReceipt.receivedAt`, notes,
`settlementKnown` (default false), reconciliation key/hash and indexes. Existing
receipt dates fall back to their creation timestamps. Totals are derived from original
items, not redundantly persisted. No historical costs or payment values are invented.

`SupplierPayment` stores business/supplier/receipt/actor IDs, amount, event date,
method, reference, notes, creation time, idempotency/hash, and an optional reversal
relationship. Composite foreign keys prevent cross-business and wrong-supplier
allocation. Customer `Payment` and existing monetary database types are unchanged.

The migration-preservation test applies the old migration chain in a fresh isolated
schema, inserts historical fixtures, applies the purchasing migration, and compares
quantities, receipt data, costs, sales and customer payments. It also verifies that
old receipts have unknown settlement state and no fabricated supplier payments.

The existing development database migration is now complete following user approval.
The procedure for another approved local database is:

1. Stop application writers and create a full PostgreSQL backup outside Git.
2. Confirm the database target privately; inspect `npm run db:status`.
3. Stop the API before Prisma generation on Windows to avoid a loaded engine DLL lock.
4. Run `npm run db:generate`, then `npm run db:deploy` (Prisma migrate deploy).
5. Verify migration status and `/api/v1/health/ready`; restart the application.
6. Reconcile historical supplier documents deliberately; do not bulk-mark them unpaid.

Never use reset, db push, destructive synchronization or automatic historical cost
recalculation. A rollback should retain additive tables/columns and settlement records;
rolling back application code does not undo payments. Prefer forward corrections.
Backup restoration must be rehearsed separately before any production cutover.

## API contracts

All paths start with `/api/v1`, require the existing session, and writes require CSRF.
Owner/manager permissions apply, except historical reconciliation is owner-only.

| Method and path                                          | Behavior                                                                                                                                                                                           |
| -------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /inventory/receipts`                               | `supplierId`, `reference`, optional `receivedDate`, `notes`, `repeatReferenceReason`, `idempotencyKey`, `items[{productId,quantity,unitCostMinor}]`; legacy top-level product fields also accepted |
| `GET /inventory/receipts`                                | Existing pagination/search plus supplier and `from`/`to` receipt-date filters; includes totals/status                                                                                              |
| `GET /inventory/receipts/:id`                            | Items, totals, settlement state and retained payment/reversal history                                                                                                                              |
| `POST /inventory/receipts/:id/payments`                  | Positive integer-string `amountMinor`, ISO `date`, `method`, optional `reference`/`notes`, `confirmed:true`, `idempotencyKey`                                                                      |
| `POST /inventory/payments/:id/reverse`                   | ISO `date`, `reason`, `confirmed:true`, `idempotencyKey`; cannot reverse a reversal or reverse twice                                                                                               |
| `POST /inventory/receipts/:id/reconcile`                 | Owner confirms `confirmAllPaymentsRecorded:true`, `reason`, `idempotencyKey`                                                                                                                       |
| `GET /suppliers/:id/financial?page=1`                    | Supplier contacts, all-time purchasing/payment totals, current verified debt, unreconciled history, paginated payment ledger                                                                       |
| `GET /reports/summary?from=…&to=…`                       | Existing summary plus purchasing, payments, current supplier debt, unknown history and expense-review count                                                                                        |
| `GET /reports/export?kind=purchases&from=…&to=…`         | Receipt-date CSV with current settlement state                                                                                                                                                     |
| `GET /reports/export?kind=supplier-payments&from=…&to=…` | Payment-date CSV including signed reversals                                                                                                                                                        |

Amounts are integer butut strings. Quantities are decimal strings, up to three places.
Totals submitted by clients are rejected. Recorded receipt/payment dates cannot be
in the future. Supplier balances are explicitly CURRENT, not balances at the selected
report end date. Payment status is derived, never a freely editable flag.

## Costing limitation and activation gate

Weighted-average costing is **not active**. Existing stock has uncertain opening values
and was created through several workflows. Existing sale-time unit-cost snapshots
remain unchanged. A tested pure arithmetic prototype adds received costs to a value
pool and proportionately allocates integer bututs across fractional issues and returns,
consuming the final residual exactly. It has no live persistence or activation endpoint.

Before activation, cost-pool persistence, allocated sale-cost snapshots, stock-count
integration, reviewed opening values, and end-to-end accounting reconciliation are
still required. Current inventory valuation and COGS retain the legacy latest-cost
method and are disclosed as estimates. This must not be presented as completed
weighted-average accounting or complete statutory profit.

## Run locally without changing the current database

Prerequisites: installed dependencies, supported Node, local PostgreSQL, and a private
root `.env` with working loopback PostgreSQL credentials. The database user needs
permission to create isolated databases. Do not paste credentials into reports.

```powershell
npm run db:generate
npm run build
npm run demo:local
```

On Windows, stop the existing API before `db:generate` if its Prisma engine DLL is
locked. Generation/build do not migrate the existing database. `demo:local` creates
and migrates a NEW `stockflow_test_demo_<random>` database, then serves:

- Frontend: `http://127.0.0.1:5175/register`
- API readiness: `http://127.0.0.1:5102/api/v1/health/ready`

Choose your own demo account credentials in registration. No password is printed or
seeded. Use illustrative data only. Product images are disabled in this isolated demo;
normal image-storage configuration is unchanged. Ctrl+C stops the demo servers.
Each run starts a fresh database; previous databases are retained, not reset or deleted.
Its database name is saved without credentials in ignored `.local/purchasing-demo.json`.
Existing `.env` values and existing application records remain untouched.

To repeat verification, run `npm run test:isolated`, frontend tests, lint, formatting,
and builds. Isolated tests create fresh databases and preserve earlier databases.
